## 1. Goal

A person has **one account** and can be a **member of several groups**, with a different role
in each. Organisers invite people into their group. No real second group is waiting
(2026-11-19), so M3 is proven with the fictional **Berlin Bears** group on Preview. A real
group goes live in production only when one asks.

## 2. Today vs target

| Concern | Today | Target |
|---|---|---|
| Identity | `players` row. Login uses the numeric `players.id` + password (`player_credentials`), or a magic-link token. | `accounts` row. Login uses email or username + password, or a magic link. |
| Membership | Implicit (every player belongs to "the" group) | `players` row with `group_id` + `account_id`; one per account per group |
| Roles | `admins` row linked to a player; `is_super`; tab locks | Per-membership role: `owner` / `admin` / `player`; tab locks per membership; `accounts.platform_role` for platform admins |
| Password reset | Admin-mediated requests (`password_reset_requests`) | Organiser-mediated per group (unchanged flow), plus email reset in M5 |
| Push | Subscription per player | Subscription per account (device); preferences per membership |
| Session (JWT) | `role`, `playerId` | `accountId`, `platformRole` only. Group role is resolved per request (M2 §4). |

## 3. Schema

```sql
CREATE TABLE accounts (
  id              integer PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
  email           text UNIQUE,                 -- nullable until email exists (M5)
  username        text UNIQUE,
  display_name    text NOT NULL,
  photo_url       text,
  platform_role   text NOT NULL DEFAULT 'user' CHECK (platform_role IN ('user','platform_admin')),
  created_at      timestamptz NOT NULL DEFAULT now(),
  deleted_at      timestamptz
);
CREATE TABLE account_credentials (account_id integer PRIMARY KEY REFERENCES accounts, password_salt text NOT NULL, password_hash text NOT NULL, updated_at timestamptz NOT NULL DEFAULT now());

ALTER TABLE players ADD COLUMN account_id integer REFERENCES accounts;
CREATE UNIQUE INDEX players_account_group_uq ON players (group_id, account_id) WHERE deleted_at IS NULL;

ALTER TABLE players ADD COLUMN group_role text NOT NULL DEFAULT 'player'
  CHECK (group_role IN ('owner','admin','player'));

CREATE TABLE group_invites (
  id          integer PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
  group_id    integer NOT NULL REFERENCES groups,
  token_hash  text NOT NULL UNIQUE,
  role        text NOT NULL DEFAULT 'player',
  max_uses    integer, used_count integer NOT NULL DEFAULT 0,
  expires_at  timestamptz NOT NULL,
  revoked_at  timestamptz,
  created_by  integer NOT NULL,                -- players.id of the inviting admin
  created_at  timestamptz NOT NULL DEFAULT now()
);
```

`accounts`, `account_credentials`, and invite-token lookups are **platform tables** with no
RLS. Only the allow-listed auth module can read them. `group_invites` has RLS for organiser
pages and a platform lookup for redemption.

### Backfill

1. Create one `accounts` row per existing player: `display_name = players.name`; copy
   `username` from `admins.username` where one exists.
2. Copy `player_credentials` to `account_credentials`. The PBKDF2 scheme is unchanged, so
   existing passwords keep working.
3. Set `players.account_id`.
4. Map `admins` to `players.group_role`: `is_super = 1` becomes `owner`, other active admins
   become `admin`. Move tab locks to key on `players.id`. Make the platform owner's account
   `platform_admin`.
5. Keep `admins` and `player_credentials` read-only for one release, then drop them
   (contract step).

## 4. Login and session

- The login form accepts **username, email, or the legacy player number**. A legacy number
  resolves through `players.id → account_id`, so the old printed instructions and saved
  passwords keep working.
- Magic-link tokens (`player_access_tokens`) resolve to a member, and therefore to an account
  and a group, and land in that group.
- The JWT carries `accountId` and `platformRole`. `resolveGroupRequest` finds the member row
  for `(group, account)` on each request: one indexed query, memoised with React `cache()`.
- A `last_group` cookie decides where `/` and legacy URLs redirect. With one membership it
  goes straight to that group; with several it shows the **group picker**.
- Header: a group switcher (name + crest) appears only when the account has two or more
  groups.
- Rate limits stay per account (`login:a<id>`).

## 5. Profiles: what is global vs per group

| Field | Scope | Why |
|---|---|---|
| Display name, photo | Account (default) with optional per-group nickname | Same person everywhere; groups may know them by a nickname |
| Preferred position, ratings, stats, awards, achievements | Member | Different groups, different football |
| Notification preferences | Member | A person may mute one group |
| Push devices | Account | A phone belongs to a person |
| Moments opt-out, sounds | Member | Group culture differs |

`players.name` stays the member's in-group display name, unique within the group (M1). It
defaults to the account's display name when the person joins.

## 6. Invitations and joining

1. An organiser creates an invite link: role, expiry (default 14 days), max uses, revocable.
   They share it in their WhatsApp group, the same way magic links are shared today.
2. A visitor opens `/join/<token>`. If they are signed in, they confirm their in-group name and
   position. If not, they register an account first (username + password; email is optional
   until M5).
3. Joining creates a `players` row in that group. The existing account-approval flow becomes
   an optional per-group setting ("new members need approval").
4. Leaving the group, or removal by an admin, sets `players.deleted_at`. History, scores, and
   money records stay intact. This is the existing soft-delete from `0012`.

## 7. Push changes

- `push_subscriptions` gains `account_id`. Backfill it from the player, then drop `player_id`
  in the contract step.
- Fan-out: members of the group → their accounts → those devices, filtered by each member's
  preferences.
- The payload includes the group name in the title (e.g. "[Sunday Ballers] Are you in?") and
  a URL built with `gp()`.

## 8. Roles and permissions

| Role | Can |
|---|---|
| `platform_admin` (account) | Create, suspend, and archive groups; view the platform console (M5); join any group **only** through an explicit, audited support mode. No silent access. |
| `owner` (member) | Everything in the group, including settings, modules, transferring ownership, and deleting the group (M5) |
| `admin` (member) | Today's admin powers, minus whatever the owner locks with tab locks |
| `player` (member) | Today's player powers |

Every group has exactly one owner, enforced by a partial unique index on
`(group_id) WHERE group_role = 'owner' AND deleted_at IS NULL`.

## 9. The pilot group

**Now:** Berlin Bears on Preview, with fictional members and one test account that is also a
member of a Preview copy of Krakow Pyramids. It exercises everything below except real users.

**Later, when a real group asks.** Choose one friendly group that is willing to:

- accept Europe/Warsaw time and PLN for now, unless M4 lands first;
- use a subset of features. The flags that already exist in `app_settings`, now per group,
  can switch some features off. Season billing can simply stay unused.
- report problems directly to us.

**Setup (platform admin, by script or a minimal `/platform/groups/new` form):**

1. Create the group (slug, name).
2. Create or link the owner's account; set `group_role = 'owner'`.
3. The owner generates invite links.

**Watch:** the isolation suite on every deploy, `app_errors` by group, and the cron fan-out
duration.

## 11. Slices (PR-sized)

1. `accounts` + `account_credentials` + backfill (read-only; login unchanged)
2. Login via account (username / player number), JWT shape change, per-request role
3. `group_role` + tab-lock move; `admins` frozen
4. Group picker, `last_group` cookie, switcher
5. Invites + join flow + optional approval
6. Push moved to accounts
7. Platform-admin flag + minimal group-creation script/form
8. **Berlin Bears pilot on Preview** (a real group in production only on request)
9. Contract: drop `admins`, `player_credentials`, `push_subscriptions.player_id`
