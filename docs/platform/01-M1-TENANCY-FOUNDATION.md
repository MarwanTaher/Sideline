## 1. Goal

Every group-owned row records which group it belongs to, and the database prevents rows from
different groups being linked. The app keeps behaving exactly as it does today because there is
only one group.

## 2. Deliverables

1. A `groups` table, seeded with group #1.
2. A `group_id` column on every group-owned table, backfilled to `1`.
3. Composite `(group_id, id)` keys on the root tables, and composite FKs from child tables.
4. Global unique constraints and singletons changed to per-group.
5. Revision triggers and functions that know which group they are in.
6. An RLS spike that proves the Neon HTTP + `set_config` mechanism. Policies are **not** enabled yet.
7. PGlite tests for all of the above.

## 3. The `groups` table

```sql
CREATE TABLE groups (
  id          integer PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
  slug        text NOT NULL UNIQUE CHECK (slug ~ '^[a-z0-9](?:[a-z0-9-]{1,38}[a-z0-9])$'),
  name        text NOT NULL,
  timezone    text NOT NULL DEFAULT 'Europe/Warsaw',  -- read by code only from M4
  currency    text NOT NULL DEFAULT 'PLN',
  locale      text NOT NULL DEFAULT 'en-GB',
  status      text NOT NULL DEFAULT 'active' CHECK (status IN ('active','suspended','archived')),
  created_at  timestamptz NOT NULL DEFAULT now()
);
INSERT INTO groups (id, slug, name) VALUES (1, 'krakow-pyramids', 'Krakow Pyramids');
SELECT setval(pg_get_serial_sequence('groups','id'), 1);
```

The founding slug `krakow-pyramids` (decided 2026-11-19) appears in every URL from M2 onwards.
Tests use a fictional second group, **Berlin Bears** (`berlin-bears`, Europe/Berlin, EUR), which
is never inserted into production. Reserve platform words: `g`, `api`, `platform`, `account`, `login`, `admin`, `new`.

## 4. Table classification

Group-owned tables get a `group_id`. Platform tables do not.

| Class | Tables | Treatment |
|---|---|---|
| **Root** (no group parent) | `players`, `matches`, `seasons`, `admins`, `app_settings`, `award_overrides`, `award_override_audit`, `score_cache_state`, `score_cache_snapshots`, `legacy_score_snapshots`, `legacy_defensive_stats`, `stories`, `seat_offers` | `group_id NOT NULL REFERENCES groups`, `UNIQUE (group_id, id)` where other tables reference them |
| **Match children** | `match_availability`, `match_guests`, `match_players`, `match_rounds`, `round_goals`, `match_scorekeepers`, `match_waitlist`, `match_motm_votes`, `match_reactions`, `matchday_settlements`, `votes`, `vote_skips`, `vote_audit`, `stats`, `stats_audit`, `player_stats_submissions`, `player_goals_claims`, `predictions`, `payments`, `guest_charges`, `multisport_scans` | `group_id` + composite FKs to `matches(group_id,id)` and `players(group_id,id)` |
| **Season children** | `season_subscriptions`, `season_invoices`, `season_credits`, `season_match_automation`, `season_match_occurrences`, `fund_adjustments`, `fund_entries`, `dues`, `match_automation_audit` | `group_id` + composite FKs to `seasons(group_id,id)` (and matches/players) |
| **Player children** | `player_achievements`, `player_kudos`, `player_moments`, `story_reactions`, `story_views`, `seat_offer_requests`, `admin_tab_locks` | `group_id` + composite FK to `players(group_id,id)` (or `admins`) |
| **Identity (becomes platform-level in M3)** | `player_credentials`, `player_access_tokens`, `password_reset_requests`, `password_reset_tokens`, `push_subscriptions`, `push_preferences` | Add `group_id` now, derived from the player. M3 moves them to accounts. |
| **Unused** | `admin_sessions` (from the Streamlit admin login; no code in `src` uses it since Auth.js) | Not migrated. Drop it in the M3 contract step. |
| **Platform** | `groups`, `app_errors` (gets a nullable `group_id` for diagnostics), `rate_limits` (created lazily by `rate-limit.ts`; buckets get a group prefix in M2) | No RLS |

The authoritative list is `tests/helpers/tenancy-tables.ts`. `tests/tenancy-inventory.test.ts`
fails when a migration (or a lazily created table in `src`) adds a table that isn't classified
there, so every new table needs an explicit tenancy decision.

## 5. Migration plan (expand → backfill → contract)

Split the work into reviewable files, one per domain area, so each file has a small blast
radius:

| File | Content |
|---|---|
| `0040_groups.sql` | `groups` table + seed |
| `0041_group_id_roots.sql` | ✅ `group_id integer NOT NULL DEFAULT 1 REFERENCES groups` on root tables; `(group_id, id)` unique indexes; `app_settings` keyed by `(group_id, key)` with a transitional `(key)` index (§6). |
| `0042_drop_admin_sessions.sql` | ✅ Drops the unused `admin_sessions` table. |
| `0043_group_id_match_children.sql` | ✅ Match children: `group_id`, `(group_id,id)` on `match_guests`/`match_rounds`, 51 composite FKs via `sideline_add_group_fk()` (NOT VALID → VALIDATE; `SET NULL (col)` form, PG 15+). |
| `0044_group_id_season_money.sql` | Season, money, and ledger tables (`dues`/`fund_entries` triggers from `0039` must copy `group_id`). |
| `0045_group_id_social_identity.sql` | Player children and identity tables |
| `0046_group_scoped_uniques.sql` | Per-group uniques and singletons (§6) |
| `0047_group_aware_triggers.sql` | Revision triggers and functions (§7) |

Notes:

- With one group, `ADD COLUMN … DEFAULT 1 NOT NULL` is a metadata-only change in modern
  Postgres, so there is no table rewrite. The dataset is small, so locks are brief.
- **`DEFAULT 1` is temporary scaffolding.** It lets today's `INSERT`s keep working unchanged.
  M2 removes it table by table once inserts pass `group_id` explicitly. Leaving it in place
  would silently file other groups' rows under group #1.
- Keep the existing single-column FKs until the composite FKs are validated, then drop them in
  the contract step (in M2, after code no longer depends on them).
- Indexes: change hot lookup indexes to lead with `group_id`, for example
  `matches (group_id, kickoff_at)`, `players (group_id, active)`, and
  `match_availability (group_id, match_id)`. Avoid duplicating indexes that composite FKs
  already create.

## 6. Global uniques and singletons → per group

| Today | After |
|---|---|
| `players_name_key UNIQUE(name)` | `UNIQUE (group_id, name)` (consider `lower(name)`) |
| `admins_username_key UNIQUE(username)` | `UNIQUE (group_id, username)`. `admins` itself is reshaped in M3. |
| `app_settings (key) PRIMARY KEY` | ✅ `PRIMARY KEY (group_id, key)` (0041). Every `ON CONFLICT(key)` writer now uses `(group_id, key)`. A transitional unique index on `(key)` keeps the previously deployed code working; M2 drops it with the `DEFAULT 1`. |
| `score_cache_state (id = 1)` | `PRIMARY KEY (group_id)`. One revision per group. |
| `award_overrides UNIQUE(award_type, scope_key)` | `UNIQUE (group_id, award_type, scope_key)` |
| `legacy_score_snapshots UNIQUE(player_id, snapshot_key)` | Unchanged; already player-scoped |
| Token uniques (`player_access_tokens.token`, `password_reset_tokens.token`, `admin_sessions.token`, `push_subscriptions.endpoint`) | Stay global. Tokens must be unique platform-wide. |

Because `ON CONFLICT` targets must match a unique constraint exactly, `0041` keeps both: the
new primary key for the new code and the transitional `(key)` index for the code deployed
before it. Apply `0041` before deploying the M1.2 code.

## 7. Group-aware triggers and functions

- **Score revision** (`0031`). Today it increments `score_cache_state` where `id = 1`. After the
  change, it increments the row for `COALESCE(NEW.group_id, OLD.group_id)`. The
  `app_settings` branch only fires for that group's scoring keys.
- **Ledger triggers** (`0039`). `dues` and `fund_entries` rows inherit `group_id` from the
  source row.
- **Automation and capacity functions** (`0037`). `sideline_public_signup_open` and the capacity
  and queue functions already lock by match/season; they keep the group from the match row.
  Leave the `'Europe/Warsaw'` literals alone in M1; M4 replaces them.
- Add a test that **every** function body in `pg_proc` belonging to the app writes `group_id`
  whenever it inserts into a group table.

## 8. RLS spike (prove it now, enable it in M2)

Goal: confirm, before M2 depends on it, that this pattern works with
`@neondatabase/serverless` over HTTP and measure what it costs:

```ts
// db.ts (spike)
export function groupSql(groupId: number) {
  return {
    query: async (text: string, params: unknown[] = []) => {
      const [, rows] = await sql.transaction([
        sql`SELECT set_config('sideline.group_id', ${String(groupId)}, true)`,
        sql.query(text, params),
      ]);
      return rows;
    },
  };
}
```

```sql
CREATE ROLE sideline_app LOGIN;            -- no BYPASSRLS; not the table owner
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO sideline_app;
ALTER TABLE matches ENABLE ROW LEVEL SECURITY;
CREATE POLICY group_isolation ON matches
  USING      (group_id = current_setting('sideline.group_id', true)::int)
  WITH CHECK (group_id = current_setting('sideline.group_id', true)::int);
```

Questions the spike must answer and write down:

1. Does `sql.transaction([...])` run in one HTTP round trip, and how much latency does it add
   per query on Preview?
2. Does a missing setting return zero rows? It should, because `current_setting(…, true)` is
   NULL and the comparison is not true. Does `WITH CHECK` reject inserts for another group?
3. How should the existing `sql.transaction` call sites (invoicing, scan allocation, matchday
   close) compose with this? They need a `groupTransaction(ctx, queries[])` variant that
   prepends the `set_config` statement.
4. Do PL/pgSQL functions and triggers still work under RLS as `sideline_app`? Find any that
   need `SECURITY DEFINER` and review them.
5. Does PGlite support `CREATE ROLE`/`SET ROLE` + RLS well enough for unit tests? If not, write
   the RLS tests as an opt-in Preview integration test, using the existing host safeguards in
   README.md.

The Neon default owner role bypasses RLS. **Production must connect as `sideline_app`**, and
migrations keep using the owner role. Add `DATABASE_URL_MIGRATIONS`, or keep migrations
manual, as today.

## 9. Application changes in M1 (minimal)

- `src/lib/group-context.ts`: `type GroupCtx = { groupId: number; slug: string; timezone: string; currency: string }`
  and `getFoundingGroup()`. It is not used widely yet.
- `feature-settings.ts` and the other settings modules: `ON CONFLICT (group_id, key)`, still
  writing group `1`.
- Score cache (`score-cache.ts`, `scores-cache.ts`): read and write the group #1 revision row.
- No route, auth, or UI changes.
